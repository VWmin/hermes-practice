## 1. 本周问题与范围

**架构问题：** 模型只提出工具名和参数，程序怎样确定工具可用、参数有效、执行范围受控，并给每个调用一个可配对的结果？

当前实现已有 `add`、工具 schema、工具结果与 `tool_call_id`，但 schema 和处理函数分别维护，参数直接传给函数，工具 ID 的异常情况尚未界定。本周围绕这些具体边界改进；保留第 1 周的模型适配、内存历史和最大调用次数。

阅读顺序（只追工具调用主路径和一条失败路径）：

1. [Tools Runtime 文档](../../hermes-agent/website/docs/developer-guide/tools-runtime.md)：工具 schema、注册表、可用性与分发的概念。
2. [注册表](../../hermes-agent/tools/registry.py) 的 `register`、`get_definitions` 附近，以及 [模型工具入口](../../hermes-agent/model_tools.py) 的 `get_tool_definitions`、`handle_function_call`：看“给模型看的定义”和“程序执行的函数”如何关联。
3. [工具调用校验](../../hermes-agent/agent/turn_tool_validation.py) 的 `validate_tool_calls` 与 [工具执行](../../hermes-agent/agent/tool_executor.py) 的顺序执行路径：看无效名称、参数和调用 ID 的结果如何处理。无需追完插件、MCP、并发或恢复分支。

自己实现：在 `add` 之外增加一个**只读**本地笔记工具，例如按关键词搜索 `mine/docs/` 下的 Markdown 文件。工具只访问固定目录，不接受任意文件路径，不写文件；限制返回条数和每条摘要长度。用一个简单的注册表或等价结构关联 schema 与处理函数，避免增加工具时漏改其中一处。可用普通函数和字典，不需要通用插件框架或新的依赖。

## 2. 建议执行顺序

### 任务 A：解释边界（约 1.5 小时）

沿一次成功调用和一次无效调用说明：工具如何进入模型请求；模型返回的名称和 JSON 参数如何进入程序；程序在哪里判断该名称是否允许、参数是否可用；为什么每个有效 ID 的调用都需要对应的 tool 结果。列出本周选择的错误行为：哪些生成错误 tool 结果交回模型，哪些直接停止 Turn。

### 任务 B：扩展最小实现（约 3–4 小时）

把工具 schema 与处理函数关联起来，保留 `add` 并增加只读笔记搜索工具。参数处理至少覆盖无效 JSON、非对象参数、缺少必需字段和未知工具名；允许按 schema 保守修正可明确转换的值，不要求通用的 JSON Schema 强校验。参数处理或工具自身发生错误时，不应让循环在没有配对结果的情况下崩溃；有有效 ID 的调用应得到相同 `tool_call_id` 的错误结果，或明确停止 Turn。按用户本次指定范围，不以“无法转换的值仍被处理函数接受”作为本周阻碍，记录其可能改变工具语义的限制；仍需保持正常数字输入的结果正确。对缺失或重复的调用 ID，明确采取安全的修复或停止行为，避免执行后产生无法配对的结果；不要求复制 Hermes 的 ID 修复机制。

一批多个工具调用可以继续串行执行。再次请求模型前，已接受的每个调用都应有且只有一个匹配结果，结果顺序与调用顺序一致。笔记工具的读取范围固定在 `mine/docs/`，返回内容有上限。

### 任务 C：验证与对照（约 1.5–2.5 小时）

用可脚本化假客户端覆盖：`add` 与笔记搜索的正常路径、同批多个调用、未知工具、错误参数、缺失或重复 ID，以及目录边界。记录消息角色、工具名、调用 ID、是否执行处理函数、结果顺序和结束原因。补一次真实模型使用笔记工具的去敏轨迹；若密钥或网络暂不可用，可先提交离线结果，真实运行保持待验证。

写下至少两点与 Hermes 的取舍：例如固定字典省去了自动发现的复杂度、固定只读目录省去了通用文件权限判断，同时分别限制了什么场景。只比较本周真正用到的机制。
