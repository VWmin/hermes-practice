- 状态：进行中；持久化初稿已评估，正常完整 Turn 的消息恢复通过；检查点、写入失败和 CLI 入口待修正。
- 预计投入：6–8 小时，沿用单用户、单进程、同步执行和单模型。
- 前置成果：[第 1 周控制流](WEEK_01.md)、[第 2 周工具边界](WEEK_02.md)；本周完成后形成可恢复对话的 v0.1。
- 推进规则：[学习大纲](OUTLINE.md)；本周通过后再制定第 4 周详细计划。

## 1. 本周问题与范围

**架构问题：** 进程退出后，怎样恢复同一个 Session 的完整消息历史？如果一个 Turn 在模型调用或工具执行中途失败，下一次启动应从哪个边界继续？

目前 `Agent.conversation_history` 只存在于内存。第 1、2 周已验证 assistant 的 `tool_calls`、匹配的 tool 结果及 DeepSeek 的 `reasoning_content` 必须保留；这些字段在保存和恢复后仍要原样进入下一次模型请求。本周只做本地单进程会话，不做长期记忆、压缩、跨进程锁或多用户权限系统。

阅读顺序：

1. [Session Storage 文档](../../hermes-agent/website/docs/developer-guide/session-storage.md)：重点看 Session 与 messages 的关系、保存和恢复边界，不追 SQLite 的全部表与 profile 分支。
2. [Hermes 持久化入口](../../hermes-agent/agent/session_persistence.py) 的 `_persist_session`、`_flush_messages_to_session_db`；[Turn 上下文](../../hermes-agent/agent/turn_context.py) 中从历史复制消息并加入本次 user 消息的路径。
3. 回到自己的 `agent.py` 和 `main.py`：标出一次 Turn 开始前、成功回答后，以及异常或预算耗尽时各有哪些消息仍在内存中。

**建议最小方案：** 每个 Session 用一个 JSON 文件保存会话 ID、system 消息和完整的消息列表。CLI 创建新 Session 时显示 ID，恢复时按 ID 加载；文件放在被 Git 忽略的本地状态目录，测试使用临时目录。保存采用临时文件加同目录替换，避免中途写入留下半个 JSON 文件。可用普通函数实现，不需要先复制 Hermes 的 SQLite 数据库。

本周采用清楚的恢复边界：只把**已完成的 Turn** 作为可恢复检查点。处理中断或失败时报告停止原因，下次启动恢复到上一个完整 Turn；当前未完成的用户输入可能需要重新提交。当前工具均为只读，未来加入有副作用工具时需重新设计中途恢复与重复执行策略。

## 2. 建议执行顺序

### 任务 A：追踪并定义 Session 边界（约 1.5 小时）

区分 Session ID、一次 Turn 与一次模型调用。画出新建、成功保存、按 ID 恢复、异常回退四条路径，列出必须原样保存的消息字段：`role`、`content`、assistant 的 `tool_calls`/`reasoning_content`、tool 的 `tool_call_id`。解释为什么恢复时不能只保存最终回答，也不能把未配对的工具消息直接交给模型。

### 任务 B：实现本地保存与恢复（约 3–4 小时）

在 `mine/src/` 中加入简单的 Session 存储与 CLI 新建/恢复入口；具体文件和参数名由你决定。新建时生成并显示 ID；恢复不存在或损坏的 Session 时清楚报错，不静默开始一个新会话。保存/加载完整历史，但不保存 API 密钥。一次 Turn 成功后写入检查点；异常或预算停止时保留上一个完整检查点，并给出明确停止原因。持久化文件不得被 Git 纳入提交。

保持 DeepSeek 的 thinking 消息字段和工具调用/结果的配对关系。恢复后再问一个问题时，发送给模型的历史应与保存前的完整历史一致。不要为本周增加通用数据库抽象、并发写入、上下文压缩或自动重试框架。

### 任务 C：验证与对照（约 1.5–2.5 小时）

用临时状态目录和可脚本化假客户端覆盖：连续两次输入后退出并恢复、带工具调用的完整历史往返、模型错误或预算耗尽后的恢复、损坏文件的明确失败。验证保存文件可解析，恢复后下一次请求含完整的 assistant/tool 配对与 `reasoning_content`，异常后不会出现孤立的 tool 消息或重复执行。补一次使用合成输入的真实模型跨进程恢复记录；如需计费调用或把本地内容发往模型，先确认本次授权范围。

写下至少两点与 Hermes 的取舍，例如 JSON 检查点比 SQLite 简单但缺少并发写与查询能力、只恢复完整 Turn 易于保证消息一致却会丢失中断中的进度。

## 5. 第一次学习：约 90 分钟起步

- **0–25 分钟：** 阅读 Session Storage 文档的架构和消息结构，写下自己的最小 Session 文件需要哪些字段。
- **25–50 分钟：** 追 Hermes 从历史构建 Turn 与保存消息的入口，画出成功 Turn 的持久化边界。
- **50–70 分钟：** 为当前 `Agent` 设计新建、保存、恢复三个接口及失败结果，不先实现数据库或压缩。
- **70–90 分钟：** 用假模型手写一个工具调用后恢复的消息序列，再写一个中断后只恢复上一完整 Turn 的可控场景。

本次结束时应能回答：为什么只保存最终文本不足以恢复工具对话？什么时候可以安全覆盖上一个 Session 检查点？中途失败后用户需要知道什么？

- **范围与证据：** 审阅 `mine/src/agent/session.py`、`agent.py`、`utils.py`、`main.py` 与 `mine/docs/week-03/session-storage.md`。使用临时目录和固定假客户端验证完整工具 Turn 的 JSON 往返、按 ID 恢复后的模型输入、API 失败、工具批次中断、写入失败和首次恢复。未读取现有真实会话正文，未运行计费请求，也未重复跑前两周离线脚本；本次未修改用户实现。
- **已验证的进展：** 正常完成的会话可按相同 ID 加载；保存前后的完整历史相等，assistant 的 `tool_calls`、`reasoning_content` 和 tool 的 `tool_call_id` 均保留。用恢复后的 Agent 再输入问题，下一次模型请求包含原先全部历史。W3-03 的完整 Turn 正常路径通过。
- **检查点边界（阻碍 W3-04）：** 当前在 user 消息追加后和每个工具结果后直接保存，与本周“只恢复完整 Turn”的约定矛盾。API 失败后重载文件，末尾仍是本次未完成的 user 消息；一批两个工具调用在第二个执行前失败时，文件里有两个 assistant 调用但仅有第一个 tool 结果。当前加载不检查完整性，后续模型请求可收到这段未完成序列。若希望学习 Hermes 的增量恢复，需要另外设计中断状态和消息补全；当前计划范围内应保留上一完整 Turn 检查点。
- **写入故障（阻碍 W3-04）：** `Session.flush` 以 `w` 直接打开正式文件，再调用 `json.dump`。用合成写入故障验证，已有检查点被截成 0 字节；上次可恢复状态丢失。需在写入成功后再替换正式检查点，且写入失败不得损坏旧文件。
- **ID 状态回归：** ID 前缀和计数器位于 `session.state`，但 `Agent.tool_calls` 访问 `session.tool_call_id_prefix` / `session.tool_call_id_counter`。缺失 ID 的调用实际抛 `AttributeError`，此前 W2-04 的修复路径在本版失效。应恢复这一已通过行为，不追加新的 ID 管理范围。
- **CLI 与本地文件：** `main.py` 固定恢复最新会话，不能从 CLI 新建、显示 ID 或指定恢复 ID；当状态目录尚不存在时，`load_session` 在 `Path.iterdir` 处抛 `FileNotFoundError`。状态路径相对于工作目录，换启动位置也会查找不同目录。`mine/sessions/` 已有实际 JSON 且未被 Git 忽略，违反本周会话文件不纳入提交的要求；本次未打开或提交它。
- **结论与下一步：** 第 3 周部分完成，尚不能结项。优先统一恢复边界并保护上一检查点，再修正 ID 状态访问和 CLI 新建/恢复入口；将会话目录加入忽略规则。随后提供临时目录的可复现验证和去敏记录；W3-06 仍待提交。
